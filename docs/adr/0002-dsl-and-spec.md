# 0002: Generic DSL and block catalogue in separate projects

Status: proposed, 2026-10-31

## Context

Until now one Mix project held both the generic part (the schema DSL, the Elixir and Swift generators, the mix tasks) and Mica's own blocks (`MicaBff.Blocks`). The tasks read `MicaBff.Blocks` directly, and Mica's namespace `Systems.BFF.Blocks` was a default inside the generator. Melle wants a hard split between the two, so that they could later be served from two repos. Prism makes the same split, with the same folder names.

[ADR 0001](../../dsl/docs/adr/0001-spec-format.md) (the spec format) stays as it is; it moves to `dsl/`, because its decisions are what the DSL and the generators implement.

## Decision

The repo has two Mix projects and no `mix.exs` at the root:

| Folder | App | Holds |
|---|---|---|
| `dsl/` | `:mica_bff_dsl` (`MicaBffDsl.*`) | The schema DSL, the Elixir and Swift generators and the Swift template, the mix tasks `bff.gen.elixir` and `bff.gen.swift`, their tests on a fixture catalogue of their own, ADR 0001 |
| `spec/` | `:mica_bff_spec` | `MicaBff.Blocks`, its example payloads (`fixtures/`), its tests, the generators' configuration, and a golden copy of the generated code |

The root keeps the README, CI and this ADR.

**Boundary rules**

- Inside `dsl/`, the generators (`MicaBffDsl.Gen.*`) read only the schema's public output, `__schema__/0` and its documented data, never the schema's internals. The generators stay in `dsl/`: a DSL is only useful with its generators.
- `dsl/` knows no catalogue: no `MicaBff.Blocks`, no block names, no `Systems.BFF.Blocks`, no mono or next-ios paths in its code, templates or tests.
- The generators take the catalogue and the namespaces as input, with no defaults: `--spec MODULE` and `--namespace NAME`, or the project's config:

  ```elixir
  config :mica_bff_dsl,
    spec: MicaBff.Blocks,
    elixir_namespace: "Systems.BFF.Blocks",
    swift_namespace: "BFF"
  ```
- `spec/` uses only the DSL's public API: `use MicaBffDsl.Schema`, the mix tasks and `MicaBffDsl.Gen.Elixir.generate/2` and `MicaBffDsl.Gen.Swift.generate/2`. It depends on the DSL with one line, `{:mica_bff_dsl, path: "../dsl"}`, and formats the DSL without parentheses through `import_deps: [:mica_bff_dsl]`.
- The generated files keep their header "Generated by mica-bff": it is the DSL's name, and it marks what a rerun may overwrite.
- CI proves the split: one job builds and tests `dsl/` on its own, one builds `spec/` with the DSL and checks that the generated code is the same as `spec/test/golden`.

**Moving the DSL to its own repo** takes two steps: move `dsl/` out (with its history, e.g. `git filter-repo --subdirectory-filter dsl`), and change the dependency line in `spec/mix.exs` to a git or Hex dependency, e.g. `{:mica_bff_dsl, github: "novasoftwarefoundation/mica-bff-dsl", tag: "v0.1.0"}`. Nothing in `spec/` refers to the DSL by path otherwise; CI's `dsl` job moves with it.

## Consequences

- A second catalogue (another product's blocks) is a second `spec/`-like project with its own config; the DSL doesn't change.
- A change to the DSL that changes generated code shows up as a failing golden check in `spec/`, and is accepted by regenerating `spec/test/golden` in the same PR.
- Two Mix projects to build and test instead of one; the README lists the commands for each.
